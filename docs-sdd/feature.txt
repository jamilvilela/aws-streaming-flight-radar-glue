the glue job:
must have a main.py file that initializes spark 4.0 on aws glue 5.0, parses the parameters (including --mode batch|streaming) and instantiates a Processor class;
must have a Processor class responsible for orchestrating reading, transformations and writing of data;
must have a Config class responsible for reading the json configuration file with the source settings and their characteristics, and returning a parsed object with the json data;
must have a Reader class responsible for reading data received in s3 in batch and streaming modes, with checkpointing functionality (cleanSource=archive). This class must receive the configuration parameters of the sources and their characteristics, read the files and deliver a spark dataframe as output;
must have a DataQuality class that receives the dataframe from reading and must apply cleansing rules and validations of expected data types, and convert the dataframe to the defined schema. The class must return a valid dataframe for the Processor flow. The class must have a way for invalid records to be sent to a Rejected folder in the Landing bucket. The DataQuality class must be able to read the source schema from the .json configuration file and perform validations dynamically for any source based on the data types;
must have a Writer class responsible for receiving the dataframe with valid data and storing it in a raw layer table, and this table will be informed through parameters in the .json configuration file containing database, table name, partitions name (list);
must write valid data to the raw layer in Delta Lake format, using Delta MERGE by primary key (cod_unico) for cross-batch dedup, resolving the physical table via the Glue Data Catalog (DeltaTable.forName) and bootstrapping the table on the first write;
must cover the 8 entities of the flight_radar schema coming from DMS: aircraft, airports, airlines, flights, aircraft_positions, countries, aircraft_types, routes.

complementary artifacts:
-unit tests with pytest mocking spark and other aws services, with 100% code coverage;
-integration test module with boto3 lib directly accessing the aws services implemented and/or used in this project, for example glue, s3, catalog tables. the tests must cover validation of service implementations, validation of existence of used services, checking of data read and data written by the glue job.
-bash scripts for deploy and rollback in the aws environment via terraform (ci-cd/deploy.sh and ci-cd/rollback.sh). artifact upload is handled declaratively by terraform (aws_s3_object), not by the scripts.
-pyspark python scripts can be implemented using data class, annotations, design patterns if interesting and if it is standard in the data engineering market, but if not interesting for this project, implement according to best practices.
-use spark config to optimize processing and cluster memory usage, passed dynamically via --conf.
-suggest new schema for etl_control table with relevant processing information.
-the glue job must be pure spark: it must not use glue apis (GlueContext, DynamicFrame, Job, getResolvedOptions).
